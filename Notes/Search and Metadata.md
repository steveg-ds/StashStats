# Search and Metadata

Within the Ravelry API, Search and Metadata act as the critical discovery layer for the platform's massive repository of Pattern Data. Because the Ravelry database contains hundreds of thousands of highly detailed crafting designs, the API does not treat metadata simply as a list of descriptive tags; instead, it uses a deeply nested, craft-specific architecture that powers advanced querying, filtering, and data analysis.

Here is how the sources describe Search and Metadata in the context of Pattern Data:

## 1. Advanced Pattern Search vs. Global Search

The primary gateway to discovering pattern data is the `/patterns/search.json` endpoint, which is structurally distinct from the platform's general global search. **While the global `/search` endpoint performs simple text-only queries returning basic information, the pattern-specific search is an advanced engine designed to process complex, granular filters**.

Developers can pass virtually any filter parameter that is available on the main Ravelry website's search interface directly into the API. For instance, a developer using the `ravelRy` R package can pinpoint highly specific designs by passing combined parameters—such as searching for `query = 'hat'` while simultaneously applying `availability = 'free'` and `fit = 'baby'`. Applications can also filter results by providing a pipe-delimited list of specific `pattern_id`s, allowing them to fetch subsets of patterns instantly.

## 2. Standardized Taxonomies: Categories and Attributes

To make pattern data universally searchable, Ravelry organizes its metadata into two standardized, hierarchical models: **Pattern Categories** and **Pattern Attributes**.

- **Pattern Categories:** This metadata defines what the physical object is (e.g., a sweater, a hat, a blanket).
- **Pattern Attributes:** This metadata defines the structural or stylistic elements of the design (e.g., seamless, top-down, cables).

The API provides specific endpoints (`/pattern_categories/list.json` and `/pattern_attributes/groups.json`) to retrieve these complete classification trees. Because this foundational metadata rarely changes, the API documentation explicitly recommends that developers cache these attribute lists for up to 24 hours to improve application performance. Within the pattern data payload itself, designs are linked to these taxonomies via bridging objects called `PatternTagging` (which links a pattern to an attribute ID) and `PatternClassification` (which links a pattern to a category ID).

## 3. Craft-Specific Technical Specifications

The metadata embedded within a Ravelry `Pattern` object goes far beyond standard descriptive text, encompassing highly technical, craft-specific specifications. When pattern data is retrieved, the metadata payload dictates the physical requirements to create the item:

- **Terminology and Methodology:** The metadata includes boolean flags like `has_uk_terminology` and `has_us_terminology` (crucial for crochet patterns where stitch names differ by region), as well as the overarching `craft` type.
- **Gauge and Density:** Patterns include exact metric requirements, such as the `gauge` and `row_gauge`, alongside a `gauge_divisor` which standardizes the measurement area (e.g., calculating stitches per 1 inch, 2 inches, or 4 inches/10 cm).
- **Material Constraints:** The data explicitly tracks the `yardage_min`/`yardage_max` or `meterage_max` required, the specific `pattern_needle_sizes` needed, and the overarching `yarn_weight`.

## 4. Community and Personal Metadata

Because Ravelry is a social platform, **pattern data is heavily enriched with metadata generated by the community's interactions.** The API returns aggregated metrics such as the `difficulty_average` and `rating_average`, which are calculated from user feedback, alongside absolute counts like `projects_count` and `favorites_count`.

Furthermore, search and metadata can be localized to the specific user making the API request. By setting the `personal_attributes` flag to true (or `1`) during a search, the API injects a special hash into the pattern results. This hash reveals the pattern's status within the authenticated user's personal "Notebook," indicating whether they have already queued, favorited, or bookmarked that specific design.

## 5. Developer Implementation Patterns

In practice, extracting this rich metadata typically involves a two-step programmatic flow. Developers first use the `/patterns/search` endpoint to query the database and return a list of matching pattern IDs with basic details. They then pass those IDs into the `/patterns.json` endpoint to retrieve the full, deeply nested metadata payloads for the selected designs. Because this resulting metadata is highly hierarchical, data scientists and developers must often build specific parsing scripts to flatten fields—like nested yarn requirements or needle arrays—into tabular formats before they can run statistical analyses or visual models.
